# Issue 4 — 容器程序 CPU 改用採樣區間差分排序

## 概述

來源：[GitHub issue 4](https://github.com/raybird/sys-monitor/issues/4)。

issue #2 的容器深度採樣用 Docker top 的 `pcpu` 排序「高 CPU 前 5」。`pcpu` 是 ps 的生命週期平均，也就是程序從啟動到現在的平均 CPU。長時間執行、此刻突然飆高的程序平均值仍然很低，排不進前 5，對凍結前的歸因幫助有限。

這個 issue 改成讀主機 `/proc/<pid>/stat`，用兩次深度採樣之間的 CPU 時間差分計算每個程序的區間 CPU，並依它排序。

採樣決策（2026-11-06 使用者回答，見 Gherkin 核准紀錄）：

- 高 CPU 前 5 改依區間 CPU 排序；詳情同時顯示區間值與生命週期平均。沒有前一筆可算區間值時，退回生命週期平均排序並標示原因。
- 每個容器每輪最多讀 1024 個程序的 `/proc/<pid>/stat`，最多花 0.2 秒；超過任一上限，該容器本輪的區間 CPU 全部記為未知，退回生命週期平均排序並標示。
- 區間 CPU 以 `cpu_interval` 存在 `process_sample` JSON 的每個程序裡，100% 為一個核心；TSV 欄位不變。前一次的每程序 CPU 時間存在既有的 `docker-counters.json`。

## 關鍵差異

| 項目 | 變更前 | 變更後 |
|---|---|---|
| 高 CPU 前 5 的排序 | ps 生命週期平均 `pcpu` | 兩次深度採樣之間的區間 CPU；沒有前一筆時退回生命週期平均並標示 |
| 每程序保存的 CPU | `cpu`（生命週期平均） | `cpu` 不變，另加 `cpu_interval`（區間值或 null） |
| 詳情顯示 | `CPU 2.1%` | `CPU 區間 85.0%（平均 2.1%）` |
| 讀取來源 | 只有 Docker top | Docker top 加主機 `/proc/<pid>/stat`（唯讀） |

```gherkin
Feature: 容器程序依採樣區間 CPU 排序

  Background:
    Given 收集器深度採樣一個追蹤中、執行中的容器
    And helper 能以一般使用者身分讀取該容器程序的主機 /proc/<pid>/stat

  # SCN-001
  Scenario: 有前一筆時依區間 CPU 排序
    Given 該容器上一次深度採樣已保存每個程序的 CPU 時間與 starttime
    When 本次深度採樣
    Then 每個程序的區間 CPU 為兩次 utime+stime 的差，除以兩次讀取之間的實際秒數，100% 為一個核心
    And 高 CPU 前 5 依區間 CPU 排序，記憶體前 5 與 D 狀態前 5 的選法不變，最多 15 個程序
    And 容器詳情每個程序顯示區間 CPU 與生命週期平均，例如「CPU 區間 85.0%（平均 2.1%）」

  # SCN-002
  Scenario: 沒有前一筆可比時退回生命週期平均
    Given 該容器沒有前一次的每程序 CPU 時間，例如第一次深度採樣、收集器重啟或 cache 失效
    When 本次深度採樣
    Then 每個程序的區間 CPU 記為未知
    And 高 CPU 前 5 依生命週期平均排序
    And 容器詳情標示「依生命週期平均排序（尚無前一筆可算區間值）」

  # SCN-003
  Scenario: PID 重用與兩次採樣之間啟動的程序
    Given 上一次與本次深度採樣之間，有程序結束、有新程序啟動，也有 PID 被重用
    When 本次深度採樣
    Then 同一 PID 但 starttime 不同的程序視為新程序，不與舊程序相減
    And 上一次採樣之後才啟動的程序，以它啟動後的 CPU 時間除以它實際存活的秒數計算區間 CPU；存活不到 1 秒的記為未知
    And 已結束的程序不出現在清單，也不留在保存的前一次資料裡

  # SCN-004
  Scenario: 超過讀取預算或無法讀取 /proc 時不給部分排序
    Given 該容器的程序超過 1024 個，或讀取 /proc 超過 0.2 秒，或 /proc 無法讀取，或 /proc 裡的程序名稱與 Docker top 回傳的不一致（例如 Docker 跑在 VM 裡，PID 指向主機上別的程序）
    When 本次深度採樣
    Then 該容器本輪所有程序的區間 CPU 記為未知，高 CPU 前 5 依生命週期平均排序
    And 容器詳情標示原因：「超過讀取預算」或「無法讀取 /proc」
    And 同一輪其他容器的採樣與主機採樣不受影響，helper 既有的 6 秒預算與 8 秒硬上限不變

  # SCN-005
  Scenario: 保存格式相容且有界
    Given 已有 issue 4 之前寫入的 docker TSV
    When 儀表板讀取新舊紀錄
    Then docker TSV 的欄位數與欄位順序不變
    And 沒有 cpu_interval 的舊紀錄照舊顯示「CPU x%」與生命週期平均的說明
    And docker-counters.json 只保留本輪深度採樣容器中仍存在的程序
```

## 風險與首要驗證

- **最大風險**：區間 CPU 算錯但看起來合理，誤導事故歸因。可能的原因是 PID 重用、時間分母用錯、clock tick 換算錯；另一個風險是讀 `/proc` 拖慢 helper。
- **風險等級與理由**：Medium。影響只限使用者層級的顯示與保存，可以回復，不涉及權限或資料損失；但這個數字是凍結歸因的線索，錯了不容易被發現。
- **首要驗證**：
  1. 建檔時已做：以一般使用者讀真實容器程序的 `/proc/<pid>/stat`。2026-11-06 在本機量測，`/proc` 沒有 `hidepid`，7 個容器共 16 個程序都讀得到 utime、stime、starttime，總共 0.36 ms，平均每個程序約 20 µs；`SC_CLK_TCK` 為 100，12 核。
  2. 實作時用假的 `/proc` 目錄做單元測試，期望值手算：已知 tick 差與秒數的區間值、PID 重用、新程序、超過預算、權限不足。
  3. 真實對照組：在主機上啟動自己的程序，先閒置一段時間再進入忙迴圈，用同一套讀 `/proc` 與計算的程式碼驗證。區間 CPU 應接近 100%，生命週期平均則明顯較低。使用者 2026-11-06 選擇在主機上做，不在容器內啟動程序（TBD-2）。
- **選擇理由**：數字正確性用手算期望值的假 `/proc` 最直接；真實對照組確認 tick、PID 與時間分母在真實環境下也正確。
- **完成證據**：假 `/proc` 測試的紅綠燈；對照組的區間 CPU 落在預期範圍；check.sh 全過。
