## 本機實證（2026-11-12，Asia/Taipei）
- 檢視 2026-11-01～2026-11-12 events.log：12 筆舊 FREEZE、5 筆 UNCLEAN；不是 17 次已確認當機。舊 FREEZE 可能受舊版跨日定位問題影響，不用來判定最新版本缺陷。
- 聚焦 2026-11-08 的 5 筆 UNCLEAN，取各自來源檔最後有效 epoch 前 1800 秒；不足窗口不補值。有效列數依序 9、175、175、165、175。
- 5 個窗口 memory full PSI 均為 0；CPU 溫度最高依序 80、71、68.375、67.5、74.25°C；I/O full PSI 最高 2.70、0.14、0.60、2.54、0.26%；D-state 最高 0、1、1、4、1。僅表示已保存樣本，不能排除最後樣本之後的突發異常。
- 全部 699 筆窗口樣本 gpu_processes=disabled；2026-11-12 最新樣本亦 disabled。這是未啟用既有選用功能，不是 GPU 無活動。
- 2026-11-08 10:12:01、11:11:22、19:10:57 的事件來源檔各有 1 個無有效 epoch 的尾列，分別含 321、325、322 個 NUL bytes；另外兩檔沒有 NUL。不推論為硬碟損壞或特定落盤原因。
- 對應 5 個 boot 的 journalctl -k 可讀，分別 1107、1125、1167、1132、1147 行，以目前 collector 相同規則比對，命中數全為 0。「沒有命中」不代表沒有故障。
- 本機已安裝 collector 與 repo v0.9.0 的 SHA-256 相同：c6859246c342005552b483cf82c942873b73a67f34cdeb691ab6eef48f7c8894。事故資料本身未記 collector 版本，不能認定事件發生時已使用 v0.9.0；正式版發布於 2026-11-08 20:49:33 +08:00，晚於上述事件。

## 缺口與最小範圍
1. TSV 讀取目前只要求非空 timestamp，NUL 尾列可能成為資料列；需要區分有效、損壞與缺資料，保留前一有效樣本。
2. 即時主機資料缺少以目前時間判斷新鮮度的明確狀態；容器對主機的相對時間差不能辨識兩者一起停止。
3. 事故資料缺少可直接判讀的觀測覆蓋：GPU 未啟用、核心不可讀／讀取失敗／成功但零命中、collector 版本。讓下次事故能區分沒有異常與沒有證據。

不自動開啟 GPU 採樣、不變更 journal 權限、不重啟服務、不進行壓力或斷電實驗。不在本議題擴充網路、多磁碟或主機程序區間 CPU。核心截斷仍是程式碼風險，但本次日誌沒有證明它造成事故證據缺漏，先不併入。

## 風險與首要驗證
規模 Medium；風險 Medium。最大風險是資料驗證過嚴而丟掉合法舊版資料，或把缺證據誤當正常。
先以合成且去識別化的正常舊格式、NUL 尾列、截斷列作對照，重現目前解析行為，再驗證修正；不能只看 UI 沒有報錯。使用固定時鐘測試新鮮度，核心讀取用成功零命中與失敗對照。實作前另做 GitNexus impact。

## 查核方法與證據邊界
2026-11-12 以 Python csv.DictReader 讀取事件 metrics 指向的檔案，先計數不可解析 epoch 的列，再以最後有效 epoch 篩選 1800 秒窗口、統計數值 min/max 與 GPU 狀態；Path.read_bytes().count(bytes([0])) 計數 NUL。journalctl --list-boots 依來源檔 boot ID 對齊，再用 journalctl -k -b <boot-id> -o cat --no-pager 及 src/freeze-monitor 的 kernel_alert_pattern 比對。正常窗口／無 NUL 檔為對照；本次非破壞性驗證，不代表 UI 修復驗收通過。
原始日誌僅留本機，公開內容不含使用者路徑、boot ID、程序／容器名稱。資料會依保留政策過期。

關聯：#1 已處理舊版跨日定位及 GPU 選用採樣；#4 是容器程序區間 CPU，與本範圍不同。2026-11-12 查核既有 issue #1、#2、#4、#5，未見相同追蹤範圍。
